# Open Questions — Toddler Synth

Living list of decisions not yet finalized. Move items out of this file (into the relevant spec doc) once resolved.

## Color / LED system
- **Hue arc for the 7 letters:** how wide an arc to compress ROYGBIV into so common chords blend into vivid rather than muddy colors. Candidate range discussed: ~180–250° of the wheel. Needs prototyping — write a script that computes blended colors for common triads against candidate hue assignments and visually evaluate before committing.
- **Chord color behavior:** when multiple notes are held, does the ring show a blended average of all held notes' hues, the most-recently-pressed note's hue, or a priority order (lowest/highest note wins)?
- **Physical button color vs. ring color mapping:** the sourced rainbow keycaps (Elacgap, 8 usable colors) are "distinct but not strictly ROYGBIV" — need to finalize which physical cap color maps to which letter, ideally matching the compressed hue-arc scheme once that's settled. Candidate hex values are recorded in `color-palette.md`, but the letter assignment itself and the blend-test validation are still undone.
- **Interior backlighting strip behavior:** planned (see `decision-log.md`) but undesigned — what does the interior strip actually do during normal play vs. Tutor mode vs. Simon mode? Candidate ideas floated: whole-case celebration pulse on correct Simon sequence, a progress-style fill during Tutor mode, distinct from (not duplicating) the ring's per-note color cue. Strip length is now chosen (16 LEDs, 23 total with the ring), so pattern feasibility can be worked out — just not designed yet.

## Menu / Simon-Learn mode
- **Menu structure:** nested (top-level = mode selection, then a song list within Tutor/Simon) vs. a single flat list mixing modes and songs together
- **Input behavior while menu is active:** do the A/G buttons stop playing notes entirely while the menu is open, since they're also the menu-exit/enter combo notes? (Current thinking: yes, menu takes over input entirely, but not fully decided.)
- **Visual feedback for entering/exiting the mode:** ring pulse/fade, OLED switching to a menu view, or both?

## Audio hardware
- **WM8960 Audio HAT — being sourced 2026-07-26 (found at half price) to test for a future iteration, not this unit.** Full codec chip: DAC + onboard Class-D speaker amp (like the current MAX98357A setup) plus proper I2C-controlled digital volume (unlike the MAX98357A's fixed GAIN-pin resistor) and a mic input that wouldn't be used here. Would replace both MAX98357A boards and their wiring with one HAT plugged directly onto the 40-pin header — a real simplification given how much wiring trouble the current dual-amp setup has caused. Not yet verified: actual rated speaker-output wattage against these 3W/8Ω speakers (given this project's already-documented "not loud enough" struggles, don't assume it's sufficient without checking), and the overlay/driver setup is more involved than `hifiberry-dac`'s one-liner (typically a vendor install script/DKMS module, not a stock Raspberry Pi OS overlay). Purely exploratory for now — nothing to test yet, no hardware in hand.
- **Amp GAIN pin now wired directly to GND (12dB) as of 2026-07-20 — still not as loud as wanted.** Started floating (9dB, chip default); moved to GND after a deliberate loudness check (`note_test.py`'s `AMPLITUDE` bumped to 0.9) still wasn't loud enough on its own. Next candidate: a 100kΩ resistor from GAIN to GND instead (15dB, max per datasheet) — not yet tried, pending confirming a 100kΩ resistor is on hand. If 15dB still isn't sufficient, the plan is to revisit amp/speaker hardware selection rather than keep pushing software gain.
- **Replacing `audio_engine.py`'s sine-wave stub with FluidSynth + a General MIDI soundfont — under consideration, not started, deliberately deferred past the Saturday gift deadline.** A separate project (`nektar-synth`, unrelated repo) already runs `fluidsynth` + `FluidR3_GM.sf2` successfully on the *identical* Pi Zero 2W board, which resolves the main open risk (CPU/RAM headroom on this specific hardware) before any ChromaCade-side work starts. The integration shape would differ from that project though: no MIDI keyboard here, so it'd use `pyfluidsynth`'s direct Python API (`noteon`/`noteoff`/`program_change`) called straight from `hardware_poller.py`'s GPIO callbacks, not a MIDI-routing bridge process. `testing/fluidsynth_test.py` is a first smoke-test script, **confirmed working on real ChromaCade hardware 2026-07-23**: loads the soundfont and plays an audible GM piano note through the existing `hifiberry-dac` ALSA output (`plughw:1,0`). Two real bugs found and fixed getting there — worth knowing before writing more `pyfluidsynth` code: (1) `sfload()` does not raise on failure, it silently returns `-1` while the underlying C library logs its own error text, so check the return value, not just wrap a try/except; (2) `pyfluidsynth`'s default `synth.gain` (0.2) is much quieter than `nektar-synth`'s proven `-g 3.0` command-line flag — set `synth.gain` explicitly (the script's `--gain` defaults to 3.0 now) or notes come out "brief and quiet." `pyfluidsynth` is pip-only on this OS (confirmed not in apt on Debian trixie) — `fluidsynth` itself and `fluid-soundfont-gm` are apt packages, and `fluid-soundfont-gm` (~140MB) is now installed on the ChromaCade Pi. If pursued further: the font encoder's curated instrument list should follow the same pattern as `nektar-synth`'s `midi_bridge.py` (a hand-picked subset of GM program numbers/names, chosen by dumping the soundfont's patch table the same way `nektar-synth`'s `docs/fontlist.txt` was generated).
