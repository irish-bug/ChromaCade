# Open Questions — Toddler Synth

Living list of decisions not yet finalized. Move items out of this file (into the relevant spec doc) once resolved.

## Color / LED system
- **Hue arc for the 7 letters:** how wide an arc to compress ROYGBIV into so common chords blend into vivid rather than muddy colors. Candidate range discussed: ~180–250° of the wheel. Needs prototyping — write a script that computes blended colors for common triads against candidate hue assignments and visually evaluate before committing.
- **Chord color behavior:** when multiple notes are held, does the ring show a blended average of all held notes' hues, the most-recently-pressed note's hue, or a priority order (lowest/highest note wins)?
- **Physical button color vs. ring color mapping — both resolved 2026-08-15, see `color-palette.md`.** Keycap hex and LED ring RGB are deliberately different values (additive light vs. reflective plastic), tuned separately. Still open: the hue-arc compression/chord-blend validation from `feature-spec.md`'s Color system section — the resolved per-letter hues are a real input to that work, not a finished answer to it.
- **Interior backlighting strip behavior:** planned (see `decision-log.md`) but undesigned — what does the interior strip actually do during normal play vs. Tutor mode vs. Simon mode? Candidate ideas floated: whole-case celebration pulse on correct Simon sequence, a progress-style fill during Tutor mode, distinct from (not duplicating) the ring's per-note color cue. Strip length is now chosen (16 LEDs, 23 total with the ring), so pattern feasibility can be worked out — just not designed yet.

## Menu / Simon-Learn mode
**Resolved 2026-08-15 — menu structure, input-while-menu-active, visual feedback, and song-selection mechanism (including no-preview) are all implemented now, see `chromacade.py`/`menu.py` and `control-layout.md`'s "Menu / mode interaction grammar" (also corrects that section's gesture, which was stale for the current C-D-E-F-G-A-B button labeling).** Simon Says memory mode is still unbuilt and NOT in the menu — only Play and Tutor are selectable modes; no game logic for Simon Says exists anywhere yet to hook up.
- **Sharp/flat mechanic for accidental-tier Tutor songs (see `feature-spec.md`'s Tier 3 candidate library) — floated 2026-08-15, not decided.** Two candidates: (1) simplest — cue the rocker switch directly, a discrete flip-to-match. (2) richer — cue a joystick bend and have the child slide toward max deflection until the pitch matches the target, rather than a discrete switch flip; turns the accidental into an ear-training/motor task instead of pressing a second control, and lines up with the "sharp/flat-as-modification" teaching pillar (`design-philosophy.md`) more directly than a binary flip does. Notably cheap to build if chosen: `play.py`'s existing `bent_letter()`/`update_ring()` crossing-detection (built 2026-08-15 for the false-bend-message fix) already computes the exact "has the bend crossed into the target letter" moment this needs — a tutor cue would just check `bent_letter() == target` instead of driving the ring's displayed color. Open: whether tier-3 songs use rocker only, joystick only, or joystick with rocker as a fallback for a frustrated toddler.

## Firmware/software architecture
- **Exact pitch-bend semitone range for the joystick — not yet decided.** Now that the note range is settled (`feature-spec.md`: C0–C8, 7 octaves, with real headroom below C0/above C8 for bend margin), the joystick's max bend-per-direction needs a number. Should be generous enough to demonstrate "sharp/flat as modification" meaningfully but not so wide it lets a held note wander into the next letter's territory, which would undercut the note-identity teaching goal.
- **Joystick click button — currently entirely unused.** The sourced KY-023 module is dual-axis with a built-in push-button (SW pin), but the design only ever wires one analog axis for pitch bend (see `hardware-bom.md`/`gpio-pin-assignments.md`). Unlike the second axis, dropping the click was never an explicit decision — it just never came up in `control-layout.md`/`feature-spec.md`/`decision-log.md`. If used, needs a spare GPIO (GPIO7/8/14/15 currently free, per `gpio-pin-assignments.md`'s budget) wired active-low with a pull-up, same pattern as the encoder push-buttons — and a defined behavior (candidate ideas not yet discussed: snap pitch-bend to zero instantly rather than waiting for spring-return, a modifier for something else while held, etc.).
- **Resolved 2026-08-15: octave encoder's push-button's function, and the font-encoder push-button's overload/state-machine question.** Both wired in `hardware_poller.py`: together they're the menu enter/exit gesture's required hold (see `control-layout.md`), and the font button additionally gets a short-click → menu-select. Disambiguation is a press/release timestamp (short click) plus checking both buttons' state when a note button's `when_held` fires — see that module's docstring for the exact approach and its known imprecision (checks a point in time, not a continuously-held duration).
- **OLED refresh rate for continuous readouts (pitch-bend, volume) — implemented at ~15Hz (`chromacade.py`'s `OLED_THROTTLE_SECONDS`), the middle of this bullet's originally-suggested 10–20Hz range, but not independently benchmarked/listened-to for lag or choppiness.** Discrete events (note press, octave/accidental/font change) redraw immediately, unthrottled. Worth a real live check before treating 15Hz as final.

## Audio hardware
- **WM8960 Audio HAT — being sourced 2026-07-26 (found at half price) to test for a future iteration, not this unit.** Full codec chip: DAC + onboard Class-D speaker amp (like the current MAX98357A setup) plus proper I2C-controlled digital volume (unlike the MAX98357A's fixed GAIN-pin resistor) and a mic input that wouldn't be used here. Would replace both MAX98357A boards and their wiring with one HAT plugged directly onto the 40-pin header — a real simplification given how much wiring trouble the current dual-amp setup has caused. Not yet verified: actual rated speaker-output wattage against these 3W/8Ω speakers (given this project's already-documented "not loud enough" struggles, don't assume it's sufficient without checking), and the overlay/driver setup is more involved than `hifiberry-dac`'s one-liner (typically a vendor install script/DKMS module, not a stock Raspberry Pi OS overlay). Purely exploratory for now — nothing to test yet, no hardware in hand.
- **Amp GAIN pin now wired directly to GND (12dB) as of 2026-07-20 — still not as loud as wanted.** Started floating (9dB, chip default); moved to GND after a deliberate loudness check (`note_test.py`'s `AMPLITUDE` bumped to 0.9) still wasn't loud enough on its own. Next candidate: a 100kΩ resistor from GAIN to GND instead (15dB, max per datasheet) — not yet tried, pending confirming a 100kΩ resistor is on hand. If 15dB still isn't sufficient, the plan is to revisit amp/speaker hardware selection rather than keep pushing software gain.
- **Replacing `audio_engine.py`'s sine-wave stub with FluidSynth + a General MIDI soundfont — under consideration, not started, deliberately deferred past the Saturday gift deadline.** A separate project (`nektar-synth`, unrelated repo) already runs `fluidsynth` + `FluidR3_GM.sf2` successfully on the *identical* Pi Zero 2W board, which resolves the main open risk (CPU/RAM headroom on this specific hardware) before any ChromaCade-side work starts. The integration shape would differ from that project though: no MIDI keyboard here, so it'd use `pyfluidsynth`'s direct Python API (`noteon`/`noteoff`/`program_change`) called straight from `hardware_poller.py`'s GPIO callbacks, not a MIDI-routing bridge process. `testing/fluidsynth_test.py` is a first smoke-test script, **confirmed working on real ChromaCade hardware 2026-07-23**: loads the soundfont and plays an audible GM piano note through the existing `hifiberry-dac` ALSA output (`plughw:1,0`). Two real bugs found and fixed getting there — worth knowing before writing more `pyfluidsynth` code: (1) `sfload()` does not raise on failure, it silently returns `-1` while the underlying C library logs its own error text, so check the return value, not just wrap a try/except; (2) `pyfluidsynth`'s default `synth.gain` (0.2) is much quieter than `nektar-synth`'s proven `-g 3.0` command-line flag — set `synth.gain` explicitly (the script's `--gain` defaults to 3.0 now) or notes come out "brief and quiet." `pyfluidsynth` is pip-only on this OS (confirmed not in apt on Debian trixie) — `fluidsynth` itself and `fluid-soundfont-gm` are apt packages, and `fluid-soundfont-gm` (~140MB) is now installed on the ChromaCade Pi. If pursued further: the font encoder's curated instrument list should follow the same pattern as `nektar-synth`'s `midi_bridge.py` (a hand-picked subset of GM program numbers/names, chosen by dumping the soundfont's patch table the same way `nektar-synth`'s `docs/fontlist.txt` was generated).

This is no longer purely hypothetical -- `audio_engine.py`/`hardware_poller.py`/`play.py` (repo root, added 2026-08-15) are a real first slice using this exact approach, fixed to Acoustic Grand Piano for now. **Measured startup cost 2026-08-15: `sfload()` of the full 140MB `FluidR3_GM.sf2` is ~6.8s of `play.py`'s ~8.6s total startup** (everything else -- imports, `fs.start()` -- is under 2s combined). Not worth chasing now (it'll run as a systemd service with the boot chime as the ready-signal, same pattern as `chromacade-boot-chime.service`), but worth remembering: trimming a custom soundfont down to just the curated instrument list, once that list exists, would cut this startup time significantly as a side benefit of that work, not just a scope/size win.
- **"Funny sounds" voice bank idea (dog bark, cat meow, burp, fart, etc.) — floated 2026-08-15, not designed.** Standard GM has nothing like this (closest built-in options are novelty SFX patches — Bird Tweet #124, plus helicopter/gunshot/applause/seashore/telephone ring — not what's wanted here). Would need a genuinely different mechanism from the GM soundfont path: short pre-recorded sample clips, pitch-shifted per note the same way a real instrument voice is (standard approach on actual toddler toy keyboards' "funny sounds" banks). Same playback pattern as the existing boot chime (a discrete audio sample) but triggered per-note-press with pitch-shifting rather than a fixed one-shot clip. Purely a toddler-delight feature, not core to the teaching goals — revisit once the curated GM instrument list itself is being built.
- **FluidSynth playback latency through ALSA `dmix` is high (~125ms) — noticed 2026-08-13 running `play_melody.py`-style scripts, not yet measured for actual button-press-to-sound.** `fluidsynth` requests a 64-sample period (16 periods); the `dmix`-based `default` PCM (set up by the WM8960 driver install's `/etc/asound.conf`) only grants 5512 samples (3 periods) — dmix exists to let multiple processes share one audio device and imposes its own coarser buffering regardless of what the app asks for. Also: FluidSynth's "Failed to set thread to high priority" warning is expected (no `rtprio` grant for the playing user) and adds glitch risk under load. Neither broke playback tonight, but both matter a lot once this is real note-press-to-sound latency, not background melody testing — a toddler mashing a key needs to hear it near-instantly. Fix candidates when this becomes urgent: target the hardware device directly (`hw:wm8960soundcard`) instead of `default`/`dmix` to skip the software-mixing overhead, and grant the audio process `rtprio` via `/etc/security/limits.d/`. Not yet actually tested with real button-to-sound latency — do that before assuming either fix is sufficient.

## Future / stretch
- **Reintroduce a cooling fan — dropped from unit #1 2026-08-16, revisit for the next build.** `chromacade-back-panel.scad` already has a print-validated 39mm fan vent cutout + mounting holes (see `decision-log.md`'s "Case geometry" section), but unit #1 shipped without a fan installed: no room for one given everything else crowded into the interior, and the heat sink in use is large enough that it wasn't needed. Worth reconsidering once the next enclosure redesign (planned imminently, a separate effort from this) has more room to work with.
- Second unit as a Raspberry Pi Pico build (cheaper, instant-on, better battery life) — shelved for now, would require rewriting the audio engine without `pygame.mixer`'s easy polyphony
- Arcade-style trackball as an alternate/additional control — shelved as too expensive for one part, revisit if a "premium" unit is ever built
- **Discrete semitone-snap bend mode, plus a separate slider control that shifts multiple held notes together like a guitar capo — floated 2026-08-15, purely future thinking.** Two distinct ideas: (1) a bend mode that snaps to exactly one semitone rather than continuous glide, as an alternate/simpler feel from the current continuous joystick bend; (2) a capo-style control (a slider was the specific idea) that transposes everything currently held together, rather than pitch-bending in place. Neither designed, no hardware implications considered yet (would a slider even fit the existing control layout, or need new hardware) -- just captured so the idea isn't lost.
- **Custom fonts recorded from real tenor/baritone ukulele — floated 2026-08-15, purely future thinking.** Would need to move past GM soundfont programs entirely for these two voices: record individual notes, build actual sample-based patches (a soundfont editor like Polyphone is the standard tool for this), and load a custom/merged .sf2 alongside or instead of `FluidR3_GM.sf2`. Meaningfully bigger scope than picking from the existing 128 GM programs -- not started, no tooling chosen yet.
- **Full read-only root filesystem + overlay-fs, deliberately deferred to the next build (unit #2+) — floated 2026-08-16.** Raspberry Pi OS has this built in (`raspi-config` → Performance Options → Overlay File System): once enabled, the root filesystem becomes read-only with a RAM-backed (tmpfs) overlay for any writes, so nothing physically hits the SD card during normal operation — makes corruption from an unexpected power loss essentially impossible, a stronger guarantee than unit #1's mitigations (see `chromacade.py`'s menu Power Off/Reboot option, and the write-reduction check done 2026-08-16: `noatime` and `/tmp`-as-tmpfs already come as Raspberry Pi OS defaults, and swap here is `zram`, i.e. compressed RAM, not disk-backed -- none of that touches the SD card already). Not done for unit #1 because it directly conflicts with the "git pull + `systemctl restart chromacade.service`" remote-update workflow just set up: with the overlay on, a `git pull`'s changes would only persist in RAM and vanish on the next reboot unless the overlay is explicitly disabled first, updated, then re-enabled -- extra friction against exactly the "Sean/an AI agent can update this remotely" flow this build depends on. Decided: worth doing intentionally for the next build's initial imaging (before anyone depends on live remote updates against it), with the enable/disable-for-updates procedure written down in this repo and referenced from `CLAUDE.md` at that time, not attempted as a retrofit on a unit already in the field.
- **Dedicated non-root `chromacade` user (or no created user at all) for the next build, instead of running as `shane` (interactive account) / root (the actual `chromacade.service` currently runs as) — floated 2026-08-16.** Unit #1 runs `chromacade.service` as root (needed for the LED ring/strip's PWM/DMA access) and the rest of the setup (SSH, Raspberry Pi Connect, this repo's checkout) under the builder's own personal `shane` account -- fine for a one-off bring-up unit, but conflates "the person who built this" with "the account the software runs as," and running the main app as root is broader privilege than it strictly needs (root is only actually required for the PWM/DMA access, not for GPIO buttons/I2C/audio in general, which can be granted to a normal user via group membership -- `gpio`/`i2c`/`audio` groups -- instead). Worth deciding intentionally for the next build's imaging: either a dedicated `chromacade` system user scoped to exactly the group memberships the app needs (cleaner separation, but PWM/DMA access specifically may still end up needing root or a capability grant -- not yet researched which), or no additional personal user created at all if the device ships to someone who isn't also its developer. Not attempted as a retrofit on unit #1 -- same reasoning as the overlay-fs item above, this is an imaging-time decision, not something to change under a live unit.
