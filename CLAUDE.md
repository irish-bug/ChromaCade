# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ChromaCade is a DIY musical learning instrument for toddlers, built around a Raspberry Pi 4B (unit #1 was a Pi Zero 2 W but is no longer available; unit #2, hostname `plinkplonk`, is the current build — see `docs/decision-log.md`'s "Platform / compute" section). It's a *teaching* instrument (note names, octave equivalence, sharp/flat-as-modification, chord color), not a performance instrument — every design/code decision should be judged against whether it helps a small child build musical intuition, not against flexibility or feature count.

The repo is organized by function:
- `docs/` — design/decision docs (philosophy, decision log, feature spec, color palette, open questions, team/task breakdown)
- `hardware/` — electronics-level docs (GPIO pin map, BOM, control layout)
- `enclosure/` — the OpenSCAD case model, its printable assets, and case-specific fit-test plates
- `testing/` — hardware bring-up/bench-test scripts and session test-plan docs, separate from the real application code below
- `audio/` — real, tracked assets and scripts: the boot chime (`boot_chime.sh`, `chromacade-boot-chime.service`), recorded Tutor/Simon feedback clips (`nopes/`, `yays/`, both git-tracked personal recordings), and `play_melody.py`. Not the audio *engine* — that's `audio_engine.py` at the repo root (see below); see `audio/README.md`.

The application/firmware code is written and real (see Repo state below) — `.github/workflows/tests.yml` runs `pytest` on every PR against a real, passing test suite, not in anticipation of one.

## Repo state (read this before assuming code doesn't exist — it does)

- **The real app lives at the repo root, not under a package directory.** `chromacade.py` is the unified app (Play mode, the mode/song menu, Tutor mode, and Simon Says, all in one persistent process — this is what actually runs on the device day to day, see its own docstring for why one process not several) plus its supporting modules, also at the repo root: `audio_engine.py` (note math + FluidSynth playback), `hardware_poller.py` (GPIO → callbacks), `menu.py` (mode/song/sequence navigation), `tutor_mode.py`/`tutor_songs.py` (Tutor sub-mode + song data), `simon_sequences.py` (Simon Says sub-mode), `sound_pools.py` (nope/yay feedback clip selection), `led_ring.py`/`led_strip.py`, `oled_display.py`, `octave_gesture.py`. `play.py` (the original standalone play-notes script, predates `chromacade.py`) still exists too — kept intentionally as a standalone dev/test tool that bypasses the menu, not dead code; see its docstring and `chromacade.py`'s docstring for the relationship.
- **A real `pytest` suite exists and passes**: `test_audio_engine.py`, `test_menu.py`, `test_octave_gesture.py`, `test_simon_sequences.py`, `test_sound_pools.py`, `test_tutor_songs.py` (repo root, alongside the modules they test) — 165 tests as of 2026-08-20, run with a bare `pytest`. These cover the hardware-free logic each module deliberately isolates (note math, menu state transitions, song sequencing, etc.) — see e.g. `audio_engine.py`'s docstring for how it draws the line between what's unit-testable and what needs real hardware (`ChromaCadeAudio` wraps FluidSynth and isn't unit tested for that reason, same as `hardware_poller.py`).

Keep new logic in the same pattern already established: plain, hardware-free/testable functions with GPIO/hardware calls as a thin layer on top, so it fits the `pytest` CI gate in `CONTRIBUTING.md`.

## Commands

**OpenSCAD** (installed at `/usr/bin/openscad`, v2021.01):
```bash
# Render both current pieces (wordmark-embossed variant) to STL
openscad -o enclosure/chromacade-pot-side.stl enclosure/chromacade-pot-side.scad
openscad -o enclosure/chromacade-blank-side-embossed.stl enclosure/chromacade-blank-side-embossed.scad

# Render the plain (no-wordmark) blank-side, kept until the embossed print is validated
openscad -o /tmp/out.stl enclosure/chromacade-blank-side.scad

# Render a specific file (e.g. test plates) to check syntax/geometry
openscad -o /tmp/out.stl enclosure/test-mk2.scad

# Check the two pieces for interference: write a small .scad file (relative
# import() paths won't resolve through a process-substitution pseudo-file,
# so this needs to be a real file) containing:
#   intersection() {
#       import("<absolute path to>/chromacade-pot-side.stl");
#       import("<absolute path to>/chromacade-blank-side-embossed.stl");
#   }
# then render it -- "Current top level object is empty" means no overlap;
# any actual geometry means a real interference to fix.

# Open the GUI preview for interactive iteration
openscad enclosure/chromacade-pot-side.scad
```
There's no build script — each `.scad` file under `enclosure/` is a standalone entry point (see Architecture below); render the specific file you're working on.

**Tests**: `pytest` (bare, no args) runs the real suite — 165 tests as of 2026-08-20, all passing, covering `chromacade.py`'s supporting modules (see Repo state above). The scripts under `testing/` are a separate thing: manual hardware bring-up tools (require real GPIO/amp hardware, not CI-safe), not what CI runs. `pytest.ini`'s `norecursedirs = testing` excludes that directory from collection so those scripts' `gpiozero`/`pygame` imports don't break CI on a runner with no hardware libs installed. `.github/workflows/tests.yml`'s `pytest || [ "$?" -eq 5 ]` fallback (exit 5 = "no tests collected") is now just a defensive no-op for the case collection ever legitimately drops to zero again — it's not the expected/normal outcome anymore, real tests collect and run on every PR.

## Architecture: the OpenSCAD case model

The case is an **arcade-cabinet profile**, split into two printed pieces as of 2026-08-17 (see `docs/decision-log.md`) by **which side wall each piece owns** — pot-side (the side wall with the volume-pot hole, plus back+bottom) and blank-side (the other side wall, plus front+shelf+panel+top). This lets each piece print with its own side wall face-down on the bed (no support needed for the 45°-angled panel — see `enclosure/case-design.md`'s "Two-piece split" section for the full reasoning). A 2D cross-section (front-to-back, points `p0`..`p5`) is extruded across the case width into a shared shell solid, then each piece is carved out of that shell via `intersection()` with a half-plane mask (split along the diagonal line between `p1` and `p5`) plus its own endcap slab — not independently-inset cuts, which is what left a stray uncut rib in the design this superseded. Each `.scad` file (all under `enclosure/`) is independently renderable (not `include`d by one another) — they share the same dimension constants by copy-paste, which is a known deliberate tradeoff, not an oversight (see git history: "Completely unlinked standalone files", "Revert to monolithic file with export toggles"). **When changing a shared dimension (`case_w`, `case_d`, `wall`, `front_h`, `shelf_d`, `shelf_a`, `panel_l`, `panel_a`) or a mount/boss position (`own_mount_boss_centers`/`pot_side_mount_yz`/`blank_side_mount_yz`, or the coordinates inside `pot_side_mounts()`/`pot_side_mount_bosses()`), update it in every file that redeclares it** — currently `enclosure/chromacade-pot-side.scad`, `enclosure/chromacade-blank-side.scad`, `enclosure/chromacade-blank-side-embossed.scad`, and `enclosure/chromacade-fit-check.scad` all carry the full block; the mount positions specifically must also stay in sync between whichever file owns a given mount (pilot bore) and whichever file(s) just need the matching clearance hole, or the two pieces' screws won't line up. After any mount-position change, re-run the interference check (see Commands above) before trusting it. **This isn't hypothetical** — despite this exact warning, `chromacade-blank-side.scad`'s `own_mount_boss_centers` drifted from `chromacade-pot-side.scad`'s `blank_side_mount_yz` by as much as 22.74mm on one mount, `pot_side_mount_yz`'s first entry silently went stale (100 vs the real 110) the moment a single-file commit moved it, and `chromacade-fit-check.scad` carried its *own* independent stale copy of that same 100-vs-110 value in **three more places** (`pot_blank_side_mount_yz`, and two hardcoded call sites in `pot_side_mount_bosses()`/`pot_side_mounts()`) that a fix to the two standalone files didn't touch at all — all found piecemeal across 2026-08-19, not in one pass. Nothing checks these arrays against each other automatically. Don't assume any mirrored array or hardcoded call-site value is current just because a comment insists it "must stay identical"; diff the actual numbers, in every file, not just the two you already fixed.

Files (all under `enclosure/`):
- `chromacade-pot-side.scad` — builds the 2D profile (`p0`..`p5`) from the dimension constants, extrudes it into the shared shell, and carves out the pot-side piece (its own endcap intersected with the shell, plus the back+bottom strips masked via `yz_half_plane(1)`). Cuts the volume-pot hole plus the back wall's power-cable passthrough and fan vent via `hardware_cutouts()`. Bores its own 4 mounting pilot holes (`pot_side_mounts()` — 2 into the bottom strip, 2 into the back strip, right at the edge nearest blank-side, screwed together along X) plus 4 clearance holes through its endcap (`pot_side_clearance_holes()`) for the mounts blank-side owns (was 5, until blank-side's shelf/panel mount was removed 2026-08-19).
- `chromacade-blank-side.scad` — same shell-partition approach, carving out the blank-side piece (`yz_half_plane(-1)`: front+shelf+panel+top) plus its own endcap. Cuts the speaker grilles, shelf controls, and panel controls via `hardware_cutouts()`. Bores its own **4** mounting pilot holes (`blank_side_mounts()` — near the front wall's bottom/top, the panel/top joint, and the top/back joint, right at the edge nearest pot-side; a 5th mount at the shelf/panel joint was removed 2026-08-19, "hanging off in space") plus 4 clearance holes (`blank_side_clearance_holes()`) for the mounts pot-side owns. **All 4 mount bosses use one technique** (`blank_side_mount_bosses()` dispatches per mount, not a uniform loop): `flat_mount_boss()` — the *same square-cylinder technique* as `chromacade-pot-side.scad`'s `square_boss()` (a true `boss_w`×`boss_w` cube flush against the true wall surface, tapered via `hull()`, wall-touching face fixed across the whole taper — **get this anchor backwards and the boss's thinnest point floats in open air instead of growing out of solid material, which `openscad` will still report as a perfectly valid manifold** — geometry validity doesn't imply printability, a real bug shipped and got caught here 2026-08-19) — called unrotated for front wall bottom/top and the top segment, and wrapped in the panel's own `rotate([-panel_a,0,0])`/`translate()` (`panel_mount_boss()`, matching `hardware_cutouts()`'s panel-local frame) for the panel/top joint mount, which explicitly uses the *panel's* angle (45°), not the shelf's (8°). Positions as of 2026-08-19: front wall bottom/top at Y=114.73 (centered in their boss — was 110, only 1.27mm of material past the bore); panel/top joint at local (y=15, matching the note-key row — "in line with the note keys" — z=-11), moved off the OLED cutout it used to overlap. Now that the joystick mounting harness is ported back in (see `joystick-mount-dev.scad` below), front_top's boss visibly sits right against two of the joystick's mounting posts in a real render — flagged as a possible blocker 2026-08-19, but **checked and confirmed a non-problem**: overlapping solid boss/post material isn't a functional defect the way overlap with something that actually needs clearance (a moving part, a screw's access path) would be — see `own_mount_boss_centers`' comment for the exact numbers if this needs re-checking after a future dimension change. **This is the current reference model for the mount/boss system** — normally the plain file would just be "kept until the embossed variant's wordmark print is validated," but `chromacade-blank-side-embossed.scad` was deliberately *not* updated to this mount system (a project rename is under consideration) and still has the earlier bare-hole, 3mm/3.5mm design. Don't assume the embossed file matches this one until it's explicitly brought up to date.
- `chromacade-blank-side-embossed.scad` — Identical to `chromacade-blank-side.scad` plus a raised "ChromaCade" emboss on the panel exterior between the OLED and LED ring, kept as a separate standalone file rather than a toggle (see `docs/decision-log.md`). The letter outlines are embedded as literal polygon data (converted from `ChromaCade-wordmark-paths.svg`) rather than `import()`-ed at render time. **Stale as of 2026-08-18** — still has the pre-boss mount system (see the note on `chromacade-blank-side.scad` above); update it to match before treating it as current.
- `test-component-holes.scad` / `test-mk2.scad` — small multi-plate fit-test files for validating individual hardware cutout dimensions (encoder bushing, joystick, rocker switch, OLED, LED ring, MX switch clip depth, speaker grille) on real hardware *before* committing to a full-case print. `test-mk2.scad` supersedes the cutouts revised since `test-component-holes.scad` — check its header comment for which plates are newer. Print these when changing any hole dimension; don't assume a dimension is correct without a fit test noted in the file's comments or `docs/decision-log.md`.
- `chromacade-fit-check.scad` — same one-file/`PART`-selector methodology as the `grokwell-PiLC` reference repo's `pi_plc_rack.scad`: embeds copies of both real pieces' geometry (`BLANK_SIDE`/`POT_SIDE`, the only two `PART` options meant to ever be printed) alongside non-printable mockup modules for every other component (pot, OLED, LED ring, LED strip, Pi 4 + HAT stack, rocker switch, both EC11 encoders, joystick), each positioned at its matching cutout's actual coordinates so `PART = "ASSEMBLY"` renders a translucent full-case clearance check. Mockup dimensions are plain named constants at the top of the file, each flagged MEASURED (matches an already-cut hole/spec) or ESTIMATE (no real caliper reading yet) — update the ESTIMATE ones as real parts get measured, that's this file's whole purpose. Its copies of `BLANK_SIDE`/`POT_SIDE` are kept in sync with the standalone files by hand, same tradeoff as everywhere else in this section.
- `joystick-mount-dev.scad` — isolated development file for the joystick (KY-023) mounting bosses, pulled out of `chromacade-blank-side.scad` per that file's own history. Two intermediate redesigns (a hull()-ramped wedge, then a plain post + an imprecise ~26mm sphere) were tried and abandoned — both added print-support/taper machinery the actual physically-printed part (commit `a4f6a10`) never needed. **Current design, since ported back into `chromacade-blank-side.scad`'s `joystick_mount_bosses()`/`joystick_mount_pilot_holes()`/`joystick_gimbal_clearance()` (and `chromacade-fit-check.scad`'s mirrored copy) — this file and the real geometry should now match:** plain vertical `joy_boss_d`=6mm/`joy_boss_h`=12mm cylinders (no taper at all, matching what actually got printed) at the board's 4 real hole positions, plus ONE sphere cut (`joy_gimbal_r`=13.5mm, 27mm diameter matching the stick hole) centered precisely on the stick hole's true center — models the joystick's real gimbal swing far more accurately than clipping against the flat hole radius ever could. `PART = "PRINTABLE"` is the print-ready coupon (posts print straight up, no support, no reorientation needed); `ASSEMBLY`/`SINGLE` are for looking, not printing. Front_top's case-joining mount boss overlaps two of these posts in the real file — checked and confirmed a non-problem (see this file list's `chromacade-blank-side.scad` entry above).

The cross-section is built from six points (`p0`..`p5`) computed via trig off the angle/length constants (`shelf_a`, `panel_a`, `panel_l`, `shelf_d`, `front_h`) — front foot → vertical front wall → tilted shelf → 45°-angled main panel → vertical back wall. `case_h` is *derived* from this chain (it's `p4[1]`), not set directly — changing any upstream angle/length shifts the overall case height. `hardware_cutouts()` in each file locates each control by re-deriving the same segment midpoints (e.g. `shelf_my`/`shelf_mz`, `panel_my`/`panel_mz`) and rotating into that segment's local frame before placing holes — this is how holes stay correctly positioned on sloped/angled faces as dimensions change.

The two pieces fasten together along X (the case's width axis), right at each piece's own edge — not across the p1/p5 seam (an earlier attempt put mounting bosses there, needing screws up to 6" long, since a piece's own wall material is cut back well short of the seam corner at any real distance from the exact edge). Each owned mount also gets a square reinforcing boss (45°-ramped toward its own bed side, same idea as the mounts themselves) around its pilot bore — a bare bore in the strip's own `wall` (5mm) material only leaves ~1mm on each side, thin enough to risk cracking under an edge-on drop impact. See `enclosure/case-design.md`'s "Fastening" paragraph for the full 9-mount M3 layout (4 on pot-side, 5 on blank-side) and the boss rationale before changing any mount position or size.

## Conventions worth preserving

- Dimensions in the `.scad` files mix inches (via `in2mm = 25.4`) for panel-level dimensions with millimeters for hardware cutout details — keep this pattern rather than converting everything to one unit.
- `wall = 5` (mm) is treated as a load-bearing constant across the `enclosure/` housing/back-panel/test files — it's referenced both for shell thickness and for computing cutout depths (e.g. countersink depths are expressed as `wall - x`). Changing it has ripple effects.
- MX switch cutouts require an exact ~1.5mm engagement layer thickness for the clips to snap — this is called out explicitly in `enclosure/test-component-holes.scad` as intentional; don't "fix" it to match general wall thickness.
